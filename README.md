# Memorex

**Личная внешняя память на обычных markdown-файлах, которой управляет модель по писаным правилам.**

Идея та же, что была с самого начала: место, куда можно складывать собственную жизнь, не пытаясь
заранее идеально определить папку, тип документа и теги. Изменилось исполнение. Роль приложения
играет сильная модель, читающая правила хранилища; роль интерфейса — Obsidian и терминал. Кода,
который бы стоял между владельцем и его заметкой, нет.

Хранилище — это каталог с пятью папками и файлом правил:

```text
CLAUDE.md            правила, модель читает их каждый ход
.claude/skills/      remember, ingest, review
sources/             оригиналы как пришли, только добавляются
memory/              страницы знаний, плоско, связи через [[wikilinks]]
actions/             открытые и закрытые действия
inbox/               входящее и пины
log/friction.md      журнал трения
```

Плюс git. Файлы остаются обычными: их читает Obsidian, ищет `grep`, версионирует `git`, и всё это
работает, когда модель недоступна.

## Что лежит в этом репозитории

Самой памяти здесь нет — она живёт в отдельном каталоге и никуда не публикуется. Здесь то, из чего
её разворачивают, и то, как до этого дошли.

| | |
|---|---|
| [`memory-kit/`](memory-kit/) | Исходники скилла `memory-setup`: правила, три скилла, миграции, сборка. Единственный источник правил — хранилища получают их копию при установке |
| [`07_ГДЕ_НУЖЕН_ИИ.md`](07_ГДЕ_НУЖЕН_ИИ.md) | Где нужна сильная модель, где хватит дешёвой или локальной, а где модель не нужна вовсе |
| [`08_РАБОТА_С_ИДЕЯМИ.md`](08_РАБОТА_С_ИДЕЯМИ.md) | Как устроено обсуждение и раскручивание идеи — операция, ради которой память и держат |
| [`from-memory/`](from-memory/) | Страницы рабочей памяти, зафиксировавшие поворот: карточки обоих проектов, программа следующего этапа, разбор чужого опыта |

## Как завести память

Собрать и поставить скилл:

```bash
cd memory-kit && ./build.sh
```

Получится `memory-setup.zip` — добавить его как скилл в интерфейсе Claude Code. Дальше создать
пустой каталог, открыть в нём Claude Code и сказать «заведи память». Три вопроса, и каркас собран.

Правила в хранилищах не обновляются сами. В нужном сказать «обнови правила памяти»: скилл сравнит
версии и прогонит миграции по ступеням, не трогая накопленное. Подробности — в
[`memory-kit/README.md`](memory-kit/README.md).

## Как проект стал таким

Memorex начинался как python-приложение: FastAPI, SQLite, неизменяемые снапшоты заметок,
персистентная очередь фоновых разборов, веб-интерфейс. Оно было доведено до рабочего состояния и
покрыто офлайн-тестами.

26.08.2026 рядом был поставлен эксперимент: проверить, не закрывается ли то же самое связкой
«правила плюс скиллы плюс markdown», без питона и веба. Условие было жёстким — неделю пользоваться
и не писать код, а решение принимать по журналу трения, а не по желанию что-нибудь построить.

03.09.2026 развилка разрешилась. Приложением за неделю не воспользовались ни разу, markdown-
хранилище ушло в ежедневную работу, а правила выделились в переносимый комплект. Приложение не
выброшено: оно лежит в ветках [`wiki-first`](../../tree/wiki-first) и
[`legacy/provenance-compiler`](../../tree/legacy/provenance-compiler), и из него вынуты уроки —
claim-компилятор был слишком ранним, wiki-first работает, интерфейс вокруг фоновых задач оказался
тупиковым, а слой действий нужен.

Возвращаться к коду можно — но по решению, а не по инерции документов. Два места, где агентная
среда объективно не справляется, уже видны: надёжный захват извне при закрытой сессии и
напоминания, срабатывающие независимо от открытого чата. Если журнал подтвердит, что они болят,
Memorex окажется не приложением, а парой маленьких сервисов под агентом.
