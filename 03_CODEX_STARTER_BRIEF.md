# Brief для Codex / coding agent

## Роль

Ты работаешь над экспериментальной локальной системой накопления знаний.

Это не Obsidian plugin и не «еще один RAG».

Проект исследует идею: **однажды извлеченное понимание должно сохраняться и дешево переиспользоваться**.

## Продуктовая цель

Создать маленькую, прозрачную, локальную систему, которая:
- принимает сырые источники;
- надежно отслеживает состояние ingest;
- сохраняет provenance;
- извлекает сущности, claims и связи;
- умеет отвечать на вопросы;
- не читает гигантский индекс при каждом запросе;
- может использовать дешевые локальные модели там, где это разумно;
- оставляет сильной модели только сложные задачи;
- умеет генерировать человекочитаемую Wiki как view.

## Не считать текущие идеи окончательной спецификацией

Документы проекта описывают направление и архитектурные принципы.

Перед крупными архитектурными решениями:
1. кратко сформулируй проблему;
2. предложи 1–3 варианта;
3. опиши trade-offs;
4. предпочти самый простой вариант, который не закрывает очевидный путь развития.

## Ключевые ограничения

1. Источники immutable.
2. Повторный ingest должен быть идемпотентным.
3. Claim без provenance — подозрительный Claim.
4. Synthesis не является evidence.
5. Не использовать LLM для того, что надежнее делает обычный код.
6. Любой LLM structured output должен валидироваться.
7. Архитектура не должна зависеть от Obsidian.
8. Не создавать тяжелую инфраструктуру без необходимости.
9. На старте предпочитать SQLite + FTS5.
10. Все derived representations должны быть перестраиваемыми.

## Приоритеты первой реализации

### P0
- source registry;
- checksum;
- ingest status;
- parser/normalized text;
- segments;
- provenance;
- CLI для добавления/просмотра источников.

### P1
- простой extraction pipeline;
- entities;
- claims;
- claim_evidence;
- повторяемость;
- structured output validation.

### P2
- query;
- FTS;
- evidence retrieval;
- answer with citations.

### P3
- relations;
- graph traversal;
- generated Markdown Wiki.

### Later
- embeddings;
- temporal claims;
- trails;
- hierarchical summaries;
- semantic lint;
- local-vs-cloud model routing;
- experiment framework.

## Что важно логировать

Для каждого LLM вызова по возможности сохранять:
- model;
- provider/runtime;
- prompt/template version;
- input/output token count;
- duration;
- success/failure;
- structured output validity;
- retries;
- cost if known.

Это важно и для отладки, и для дальнейшего сравнения моделей.

## Стиль разработки

Предпочитать:
- маленькие модули;
- понятные структуры данных;
- schema migrations;
- тестируемые pipeline stages;
- deterministic code;
- fixtures;
- CLI-first.

Избегать:
- скрытого состояния;
- магии;
- слишком умных агентов;
- auto-fix без audit trail;
- невалидируемых JSON-like ответов моделей;
- жесткой привязки к конкретному LLM provider.

## Первый ожидаемый результат

Небольшой CLI-проект, в котором можно:
1. добавить файл;
2. увидеть, что он зарегистрирован;
3. повторно добавить и убедиться, что он не обрабатывается заново;
4. получить normalized text и segments;
5. извлечь несколько claims;
6. открыть claim и увидеть точный evidence;
7. задать простой вопрос;
8. получить ответ с указанием evidence.
