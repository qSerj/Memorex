# Развёртывание памяти

Сценарий: создан пустой каталог, в нём запущен Claude, вызван этот скилл. На выходе каталог
становится хранилищем внешней памяти под управлением модели: правила, три скилла, пять папок,
git с первым коммитом.

Всё пишется **в текущий рабочий каталог**. Ни в каталог скилла, ни в домашний, ни в соседний.
Если непонятно, где мы находимся, сначала `pwd`, и только потом что-то создавать.

## Разрешение путей

Два разных корня, и путать их нельзя:

- **Чтение** `references/<файл>.md` относительно каталога, где лежит **этот** SKILL.md.
- **Запись** `./<путь>` относительно каталога владельца.

Если Read не открывает `references/...` напрямую (в разных сборках скилл монтируется по-разному),
найти каталог один раз перед фазой A и дальше пользоваться абсолютным путём:

```bash
find ~/.claude ~/.config/claude / -type d -path '*memory-kit/references' 2>/dev/null | head -1
```

Не повторять поиск для каждого файла.

## Проверка перед стартом

### Не внутри ли мы чужого репозитория

Первым делом, до всего остального:

```bash
git rev-parse --show-toplevel 2>/dev/null
```

Если команда что-то вернула и это **не** текущий каталог, значит мы внутри уже существующего
репозитория, скорее всего внутри рабочего проекта. Тогда `git init` и `git add -A` из фазы C
недопустимы: первый создаст вложенный репозиторий молча, второй заметёт в индекс весь проект
вместе с недописанным кодом.

Остановиться и спросить, как жить с историей:

- **Свой репозиторий внутри проекта.** У памяти отдельный `.git`, в `.gitignore` проекта
  добавляется её каталог. История памяти и история кода не смешиваются, `git log` памяти снова
  читается как журнал операций. Память не уедет при клонировании проекта: её носят отдельно.
- **Общая история с проектом.** `git init` не делать, коммитить в репозиторий проекта. Тогда в
  каждом коммите указывать **только пути памяти**, никогда `git add -A`, иначе в коммит про
  сохранённую мысль попадёт незаконченный код. `git log` памяти смотреть как
  `git log -- <каталог памяти>`.
- **Отмена**, если стало понятно, что памяти здесь не место.

Выбор записать в `CLAUDE.md` памяти отдельной строкой, чтобы в следующей сессии не гадать.

### Не развёрнуто ли уже

Посмотреть, есть ли `CLAUDE.md` **в самом текущем каталоге**. Не искать в подкаталогах и не
подниматься вверх.

**Если нет**: обычная установка, фазы A, B, C.

**Если есть**: хранилище уже развёрнуто, и дальше всё решает версия. Прочитать свою версию из
файла `VERSION` рядом с этим SKILL.md, а версию хранилища из frontmatter его `CLAUDE.md`:

```yaml
---
memory-kit: 1.0.0
установлено: 2026-08-26
---
```

Frontmatter нет вообще, значит хранилище доисторическое, считать его версию `0.0.0`.

| Сравнение | Что делать |
|---|---|
| версия хранилища меньше | предложить обновление, см. ниже |
| версии равны | предложить переустановку правил на случай, если файлы правил повредились. Миграции не гонять |
| версия хранилища больше | **отказаться и остановиться**. Комплект старее хранилища, и накатывать старые правила на новые данные нельзя. Сказать обе версии и предложить обновить комплект |

Удаления и сброса здесь нет ни в одной ветке. Развёрнутое хранилище содержит чужую работу, и
стирать её скилл не имеет права ни при каком ответе. Нужен чистый старт, создаётся новый каталог.

### Обновление

Показать, что произойдёт, и получить согласие: с какой версии на какую, какие ступени миграций
будут пройдены, сколько файлов затронет каждая. Молча не обновлять.

Порядок:

1. **Потребовать чистый рабочий каталог.** Есть незакоммиченные изменения, значит сначала коммит
   или откладывание. Обновление поверх грязного каталога лишает владельца возможности отличить
   свои правки от моих.
2. Коммит состояния «до»: `до обновления правил: X.Y.Z`.
3. Заменить скиллы в `.claude/skills/` и тело `CLAUDE.md`. **Шапка `CLAUDE.md` до раздела
   «Структура» сохраняется дословно**, вместе с frontmatter: это лицо конкретного хранилища, и
   комплект его не знает. Обновляется только строка `memory-kit:`.
4. Прогнать миграции цепочкой по возрастанию версий, из `migrations/`, по файлу на ступень.
   Пропускать ступени нельзя. После каждой отдельный коммит с номерами версий. Ступень, для
   которой файла миграции нет, означает, что правки данных не требуется: пройти дальше молча.
5. Показать `git diff --stat` и назвать вслух, что миграции не смогли или не стали делать.

**Память, источники, действия и журнал трения обновление не трогает.** Их меняют только миграции,
и только по правилам из `migrations/README.md`, где главное правило одно: массив информации
сохраняется. Миграция меняет форму, а не содержание. Если после обновления в хранилище стало
меньше сведений, чем было, это ошибка, а не улучшение.

Если миграция сомневается в конкретной странице, она эту страницу пропускает и называет в отчёте.
Честно недоделанная половина лучше, чем сделанное всё с тремя незаметно испорченными страницами.

## Фаза A. Каркас

Без вопросов, молча.

```bash
mkdir -p .claude/skills/remember .claude/skills/ingest .claude/skills/review
mkdir -p sources memory actions inbox log
touch sources/.gitkeep inbox/.gitkeep
```

Из `references/` записать как есть:

| Читать | Писать |
|---|---|
| `references/skill-remember.md` | `./.claude/skills/remember/SKILL.md` |
| `references/skill-ingest.md` | `./.claude/skills/ingest/SKILL.md` |
| `references/skill-review.md` | `./.claude/skills/review/SKILL.md` |
| `references/friction-log.md` | `./log/friction.md` |
| `references/actions-open.md` | `./actions/open.md` |
| `references/actions-done.md` | `./actions/done.md` |
| `references/gitignore.md` | `./.gitignore` |

Эти семь копируются **дословно**, без правок. Правила выстраданы на реальном использовании, и
новое хранилище должно стартовать с той же точки, а не с урезанной под свежую тему.

`references/claude-md.md` и `references/memory-identity.md` содержат `{{плейсхолдеры}}` и
записываются после знакомства, в фазе C.

Скилл `memory-setup` в хранилище **не копируется**. Он живёт снаружи и один на все хранилища,
иначе копии разойдутся и обновлять правила станет негде.

## Фаза B. Знакомство

Три вопроса одним коротким сообщением, свободным ответом. Не форма, не анкета.

> Три вопроса, отвечай как удобно, хоть одним абзацем, хоть надиктовкой.
>
> 1. Что это за хранилище и для чего. Своими словами, чем подробнее, тем меньше шаблона получится.
> 2. Если хранилищ у тебя несколько: почему это отдельное. Конфиденциальность, чужие дела или
>    конечный срок жизни.
> 3. Будут ли здесь производиться документы, которые кому-то отдают или подписывают: договоры,
>    регламенты, чеклисты, спецификации. Да или нет.

Дальше **не расспрашивать**. Ни уточнений, ни второго круга, ни двенадцати категорий про бренд,
клиента и приоритеты года.

Длинное интервью на входе противоречит самой идее этого хранилища. Оно заранее решает, из каких
частей состоит жизнь владельца, и раскладывает будущее знание по придуманным до знакомства полкам.
Здесь наоборот: структура рождается из материала. Хранилище узнаёт владельца тем, что он в него
кладёт, а не тем, что он про себя рассказал в первый день.

Если владелец отвечает «просто заведи», ответы считаются пустыми и фаза C идёт по минимуму:
страница назначения пишется в одну строку, `documents/` не создаётся.

## Фаза C. Сборка

### C.1. CLAUDE.md

Прочитать `references/claude-md.md`, заменить `{{плейсхолдеры}}` ответами из фазы B, записать в
`./CLAUDE.md`.

`{{ВЕРСИЯ}}` берётся из файла `VERSION` рядом с этим SKILL.md, `{{ДАТА}}` это сегодня. Эти два
поля не косметика: по ним следующий запуск поймёт, надо ли обновлять правила и какие миграции
прогонять. Забыть их проставить значит сделать хранилище доисторическим.

**Шаблон это заготовка, а не результат.** Ни одной фигурной скобки в записанном файле остаться не
должно. Если данных на блок нет, блок **удаляется целиком**, а не заполняется словами «не указано».
Хранилище единственное, значит строка про причину отдельности выбрасывается.

Слова владельца использовать его же. Он сказал «разбор конфиденциального проекта с советами от
модели» — так и писать, а не «управление проектной информацией».

### C.2. Страница назначения

`references/memory-identity.md` → `./memory/{{Название}}.md`. Те же правила: плейсхолдеры
заменяются, пустые блоки удаляются, формулировки берутся из ответа владельца дословно.

Это первая страница памяти и точка привязки для будущих ссылок.

### C.3. Раздел documents, если ответ на третий вопрос «да»

```bash
mkdir -p documents
```

Дописать в раздел «Структура» в `CLAUDE.md`:

```text
documents/ произведённые артефакты: договоры, регламенты, чеклисты, спецификации.
           Правила сжатия и переписывания сюда не применяются никогда.
           Каждый документ несёт версию и дату. Прежние версии не затираются.
```

Отделять их от `memory/` нужно по существу, а не для порядка: к памяти применяется сжатие
разросшихся страниц, а к договору применять сжатие нельзя ни при каких обстоятельствах.

Если ответ «нет», папку не создавать. Появится первый документ, появится и папка.

### C.4. Git

Отдельный каталог или свой репозиторий внутри проекта:

```bash
git init -q && git symbolic-ref HEAD refs/heads/main
git config core.quotepath false
git add -A && git commit -q -m "Развернуть память: <название>"
```

Если выбрана общая история с проектом, `git init` **не делать**, а закоммитить только пути памяти:

```bash
git add <каталог памяти> && git commit -q -m "Развернуть память: <название>"
```

`git add -A` в чужом репозитории запрещён навсегда, не только при установке. Владелец почти всегда
держит в работе незаконченные правки, и заметать их в коммит про память нельзя.

`core.quotepath false` обязательно: без неё кириллические имена файлов в `git status` выглядят
как `\320\237\321\200`, и читать историю невозможно.

Если git недоступен, сказать об этом прямо и не молчать. Без него не работает откат, а вся защита
памяти от испорченной правки держится на нём.

## Итог

Коротко, без перечисления каждого файла:

- где развёрнуто и из какого комплекта;
- какие правила поставлены, одной строкой;
- номер первого коммита;
- что делать дальше: положить первый материал в `inbox/` или просто сказать «запомни».

Отдельно назвать вслух, если причина отдельного хранилища была в конфиденциальности:

- отдельный каталог не делает содержимое защищённым, файлы лежат открытым текстом;
- носитель, который уезжает из дома, шифруется целиком, а не пофайлово;
- разговор с моделью о содержимом это тоже вынос наружу, и правила хранилища на это не влияют.

Не решать это за владельца, просто сказать один раз.

## Про расхождение правил

Комплект это единственный источник правил. Хранилища получают копию в момент установки и дальше
живут сами.

Когда правка правил понадобится сразу нескольким хранилищам, обновлять их надо здесь, в комплекте,
а потом прогонять `memory-setup` в каждом хранилище с ответом «обновить правила». Правка, сделанная
внутри одного хранилища и не перенесённая сюда, потеряется при следующем обновлении. Это стоит
сказать владельцу один раз при первой же установке второго хранилища.
