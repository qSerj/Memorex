# LLM Knowledge Lab — контекст и замысел

## Зачем вообще этот проект

Цель — построить локальную, практически полезную систему накопления знаний, с которой удобно работать AI-агентам и человеку.

Отправная идея — LLM Wiki / Memex-подобная база знаний:
- есть сырые источники;
- модель извлекает из них важные знания;
- знания связываются между собой;
- на запрос модель получает не весь корпус, а нужный контекст;
- понимание, однажды полученное дорогой моделью, по возможности сохраняется и переиспользуется.

Система должна быть пригодна не только для демонстрации, но и для реального постоянного использования: личные знания, заметки, стенограммы разговоров, рабочие документы, обсуждения проектов, исследования, документация, результаты экспериментов с AI/LLM и, возможно, в дальнейшем исходный код.

## Основной принцип

Не заставлять LLM снова и снова понимать одни и те же данные.

Вместо:

> каждый запрос → перечитать много исходников → заново понять → ответить

желательно:

> источник → один раз дорого обработать → сохранить структурированное знание → много раз дешево использовать

Это можно рассматривать как **кэширование понимания**.

## Что важно сохранить из идеи LLM Wiki

1. Сырые источники должны оставаться неизменяемыми.
2. Производное знание должно быть читаемо человеком.
3. Система должна уметь добавлять знания, обновлять их, находить связи, отвечать на вопросы и проверять накопленную базу.
4. Человек должен иметь возможность видеть, откуда взялось утверждение.
5. Система не должна зависеть от одной конкретной LLM, UI или формата заметок.

## Почему простая схема `raw/ → wiki/index.md → Markdown` недостаточна

Минимальная демонстрационная схема имеет несколько очевидных проблем:
- невозможно надежно определять новые/измененные файлы только рассуждением модели;
- единый `index.md` растет и начинает дорого попадать в контекст;
- повторный ingest может дублировать знания;
- нет строгой модели изменения/отмены фактов;
- нет политики версий и сроков действия утверждений;
- нет надежного provenance до конкретного места в источнике;
- хорошие ответы модели могут начать загрязнять Wiki, если принять их за первичный факт;
- `lint` смешивает машинно-проверяемые ошибки и семантические выводы;
- `[[wikilinks]]` показывают наличие связи, но не ее тип;
- Markdown одновременно пытается быть и хранилищем, и индексом, и пользовательским интерфейсом.

## Ключевой архитектурный поворот

Markdown Wiki не должна быть единственной базой знаний.

```text
                    ┌── Markdown Wiki
                    ├── HTML / UI
RAW → Knowledge DB ─┼── Graph View
                    ├── Agent Context
                    └── Reports
```

То есть Markdown — это один из **views** поверх структурированного состояния.

## Что считать ядром системы

Минимальные сущности:
- **Source** — первоисточник.
- **Segment / Evidence** — конкретный фрагмент первоисточника.
- **Entity** — сущность или понятие.
- **Claim** — атомарное утверждение.
- **Relation** — типизированная связь между сущностями/утверждениями.
- **Synthesis** — производное обобщение/страница/ответ.
- **Trail** — сохраненный маршрут через знания, приведший к выводу.
- **Job / Processing State** — состояние обработки источника.

## Очень важное правило доверия

**Synthesis не является evidence.**

Если модель сформировала красивый итог, он может быть сохранен как производное знание, но сам по себе не становится первоисточником фактов.

Любой Claim должен в идеале иметь ссылку на Evidence, а Evidence — на Source.

## Временная модель

Нужно учитывать, что знания меняются.

Предпочтительно не переписывать старое утверждение без следа, а хранить:
- `valid_from`;
- `valid_to`;
- `supersedes / superseded_by`;
- `observed_at`;
- confidence;
- статус актуальности.

Это дает нормальные ответы на вопросы:
- что верно сейчас;
- что считали верным раньше;
- когда решение изменилось;
- почему старый документ противоречит новому.

## Retrieval не должен быть одним способом

Разные запросы требуют разных механизмов:
- точный / полнотекстовый поиск;
- BM25/FTS;
- vector search;
- поиск по сущностям;
- обход графа;
- временной поиск;
- многоуровневые summaries;
- сохраненные trails.

Потенциальная схема:

```text
QUESTION
   ↓
cheap router
   ↓
┌──────────────────────────────┐
│ exact / FTS / BM25           │
│ vector similarity            │
│ graph traversal              │
│ temporal lookup              │
│ hierarchical summaries       │
│ saved trails                 │
└──────────────────────────────┘
   ↓
merge / rerank / token budget
   ↓
LLM
```

## Роль маленьких и больших моделей

Модель не нужна там, где задачу решает обычный код: checksum, поиск новых файлов, dedupe, FTS, графовый обход, проверка схем и ссылок, job state, token budgeting.

Малые локальные модели можно пробовать для классификации, entity extraction, простых summaries, candidate relation extraction, query routing и reranking.

Сильные модели оставить для сложного synthesis, трудного entity resolution, неоднозначных отношений, contradiction reasoning и глобальных вопросов.

## Obsidian

Obsidian не должен быть частью ядра.

Он может быть удобным frontend: просмотр Markdown, backlinks, `[[wikilinks]]`, graph view, ручное чтение и редактирование производных представлений.

Система должна продолжать работать без Obsidian вообще.

## Рабочее название

Пока можно использовать **LLM Knowledge Lab** или **Knowledge Compiler**.

Термин «compiler» отражает идею: сырые материалы компилируются в более структурированное знание.
